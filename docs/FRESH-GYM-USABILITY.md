# Fresh gym usability evaluation

Evaluated 18 October 2026. Synthetic persona: Arun, an intermediate lifter training four days weekly, already knows his planned exercises, uses one sweaty hand between sets, encounters occupied machines, and wants accurate logging and next-week comparison. This is an expert walkthrough using that persona, not actual human research. No human participants, measured completion times, or empirical frustration ratings.

## Method and evidence

Used only the rendered `docs/design/dot-direction.html` initially and throughout; did not inspect application source or other product/design documentation. Chromium via Playwright rendered standalone HTML with `setContent`, at 390 × 844 and 320 × 740. Actually clicked review/start, reuse previous numbers, log, edit/apply, swap/accept replacement, home/progress, finish/confirm, and opened a fresh page. Screenshots and DOM bounds are in `tests/artifacts/fresh-usability/`. Bounds are CSS pixels. Desktop automation does not reproduce sweat, actual thumb reach, a mobile keyboard, screen-reader use, or real gym distraction.

## Journey observations

- **First visit:** Clear notebook hierarchy and prominent Review workout; visit chart and exercise graphic consume substantial space before action. Banner and footer disclose example/memory status. The first screen shows Chest day, 3 exercises, 9 sets and 8–12 reps, adequate context for Arun to recognize the plan.
- **Start:** Review exposes plan and equipment, gym field, and a clear Start workout button. The start button falls beneath the initial viewport; known-plan entry is slower than the dominant home action suggests.
- **Log:** Use copies 60 kg × 8; Log set 1 advances to Set 2, preserves working values, and changes count to 1/9. Weight/reps inputs have decimal/numeric input modes respectively. Large 61-pixel fields and 44-pixel increment controls support quick taps. Weight increments are 0.5 kg; changing a plate-sized load by repeated taps is cumbersome, although direct input is available.
- **Busy machine:** Swap is named, visible, and 44 pixels high. Sheet explains load review and cleared unlogged numbers. Accepting replacement changes the exercise and removes misleading old-load reference. Only one replacement choice and unclear dumbbell weight convention remain limitations.
- **Correct mistake:** A 44 × 44 pencil control with accessible name “Edit set 1” opens a sheet. Apply correction works. The control is below the fold after the first log; icon-only presentation is less discoverable during distraction than a visible Edit label.
- **Finish partial:** Finish opens confirmation with logged count and explicit “Unperformed sets stay unrecorded. Your plan remains unchanged.” Finish example workout returns home and increments visits. This is good protection against fabricating completed sets; it needs a clearer receipt.
- **Return later/comparison:** Home preserves an in-memory active workout as Continue workout when returning via Home. A fresh page resets to example records. Progress details disclose illustrative first/latest records and comparison conditions, but cannot compare Arun’s newly logged work.

## Controls and accessibility limits

Observed principal buttons and icon actions have at least 44-pixel height, with wide log/start actions. Numeric inputs have accessible labels and appropriate input modes. The checkbox itself is 18 × 18; its surrounding label may enlarge its clickable region, so the checkbox dimensions alone do not establish a hit-area failure. At 320 width exercise names wrap rather than overlap, and the swap sheet remains legible. Top Home/Finish actions demand higher reach than the lower log control. Screen-reader navigation, contrast ratios, actual mobile keyboard occlusion, accidental double-taps, and physical one-handed usability were not tested.
